§ 06 — Self-hosted

My home server.

I run a small mini PC at home with Ubuntu Server on it. It handles DNS for the house, my password manager, a media server and a dashboard, about fifteen containers in all. I could have had most of it running in a weekend. I took longer on purpose and set up the certificates, networking, backups and deploys before adding more services, because those are the parts that are painful to fix later.

// The foundation

Before adding more services I wanted these settled:

01

One stack per service

Each service has its own Docker Compose folder in git, so a change shows up as a diff and I can revert it.

02

HTTPS for everything

Caddy serves ten internal names behind a single Let's Encrypt wildcard certificate (Cloudflare DNS-01).

03

Ports and secrets

Docker-published ports skip the ufw firewall, so I bind each one to a specific host IP. The .gitignore is an allowlist, so I can't commit a secret by mistake.

04

Pinned subnets

I fixed the Docker subnets so a routing rule can't end up matching the wrong network.

05

Testing

I restored a backup before trusting it, rebooted three times to check the routing held, and tried to sneak a test signature past the antivirus.

06

Documentation

A setup guide, a runbook for each part, and architecture diagrams generated from code so I can regenerate them when something changes.

// CI/CD

The config for the whole server is in a private GitHub repo, and merging to main is how changes get onto the machine. The GitHub Actions runner lives on the server itself and only makes outbound connections, so deploys need no open inbound port and no SSH key stored in GitHub.

  1. pull request branch ruleset on main
  2. validate + secrets compose check · gitleaks
  3. merge checks must be green
  4. self-hosted runner outbound HTTPS only
  5. deploy.sh --ff-only · --wait
  6. verify red → rollback + phone alert
  • Deploys run as a user with no password and no sudo. I used POSIX ACLs instead of chown -R, so it can only touch tracked files.
  • deploy.sh only deploys stacks on an allowlist and refuses to run if the server has uncommitted edits. It uses --ff-only and --wait, so a bad deploy fails the job.
  • A ruleset on main requires a pull request, a Compose config check and a gitleaks scan to pass before anything merges.
  • If the new version isn't healthy, the server rolls back to the previous commit and sends a notification to my phone.
  • The DNS, VPN and proxy stacks are marked manual. A merge updates their files, but I restart those myself.
// Drift detection

Deploys cover changes I make through git. Two scheduled workflows check for everything else, like a container I started by hand or a file I edited on the server. The repo is the source of truth, and neither workflow ever pushes server state back to it.

hourly · 17 * * * *

Enforce

Is every running container from a stack in the repo?

  • If not, the container is stopped and its restart policy is set to no, so it doesn't come back after a reboot. I keep its settings and last logs to look at.
  • The run is marked as failed on purpose, so I get notified.
  • To allow something, I add it to a committed allowlist in a pull request.
nightly · 03:07 HKT

Heal

Does the server still match the repo?

  • Hand-edited tracked files are saved as a patch, then restored to what git has.
  • Stopped containers are started. Unhealthy ones get one restart and 60 seconds to recover, with a cap of ten actions per run.
  • DNS, VPN and the proxy are only reported, never restarted, since a restart at 3 a.m. would drop the network.
  • Unused images, networks and build cache are cleaned up. Volumes are listed but never deleted.
// Networking
  • DNS. AdGuard Home filters DNS for the whole house and resolves the ten internal names locally.
  • Remote access. Tailscale, with an exit node and a subnet route, makes the same names work from my phone and laptop when I'm away.
  • VPN. The router runs a ProtonVPN WireGuard client, and a per-device list decides which devices use it.
  • Routing on the server. Linux policy routing (netplan, ip rule, a dedicated routing table and ARP sysctl tuning) decides which traffic goes through the VPN. The Docker subnets are pinned so the rules stay predictable, and I rebooted three times to confirm they persist.
// Other pieces

Backups

restic encrypts backups every night before they go to Backblaze B2. SQLite databases are snapshotted first so the copies are consistent, and Healthchecks.io alerts me if a backup doesn't arrive. When I tested a restore, every database passed an integrity check and Uptime Kuma came back with all 19 monitors. The test also showed the backup service was running without a restic cache and taking 8 minutes. One line fixed that, and it now takes about 30 seconds.

Antivirus scanning

ClamAV scans every file before it reaches the media library. When I hid a harmless test signature deep inside a large file, it wasn't caught: stream scanning only reached about 90 MB, and ClamAV can't scan a single file over 2 GiB. Large files are now split into overlapping slices. I confirmed it with a marker near the end of a 2.5 GB file, which now gets quarantined.

Monitoring

Uptime Kuma checks services, Beszel tracks host metrics and ntfy sends alerts to my phone. Healthchecks.io works as an external dead-man's switch, so I find out if the whole server goes down.
